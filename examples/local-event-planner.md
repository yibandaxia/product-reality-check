# Example — Local Event Planning Assistant

## Starting idea

> I want to make an app that recommends interesting things to do nearby on weekends.

## First risk

The idea sounds attractive, but the initial problem statement is too broad.

"People want things to do" does not prove that they need a new product.

## Discovery path

### 1. Identify the triggering moment

Ask:

> When does someone actually start searching for something to do?

Possible answers:

- Friday afternoon after work
- when friends visit
- on a date
- when travelling to another city
- when parents need activities for children

Each is a different product opportunity.

### 2. Inspect current alternatives

Ask:

> What do people use today?

Possible alternatives:

- search engines
- social media
- local newsletters
- ticketing platforms
- maps
- group chats
- asking friends

If these already solve the job well enough, a generic recommendation app may struggle.

### 3. Look for a narrower wedge

A stronger niche might be:

> Parents with children aged 4–8 who want to find bookable weekend activities within a short travel radius.

This is narrower but easier to test because:

- the user is identifiable
- the timing is recurring
- constraints are concrete
- the value of filtering is clearer

### 4. Test distribution

Ask:

> Where could the first 100 users come from?

Possible channels:

- local parent communities
- school newsletters
- city-specific search terms
- family activity groups

### 5. Minimum validation

Do not build the app first.

Test a manually curated weekly list for one city and one audience.

Measure:

- open rate
- click-through rate
- repeat use
- booking intent
- referrals

## Example diagnosis

**Demand status:** Real problem, likely wrong initial product scope.

**Critical assumption:** A narrow group values curation enough to return every week.

**Cheapest next test:** A manually curated weekly recommendation list for one audience in one city.
