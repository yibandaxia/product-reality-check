# Product Reality Check｜需求鉴真

> 一个偏怀疑主义的产品经理 Skill：把模糊的产品想法，拆成可以验证的产品假设。

AI 正在显著降低“把东西做出来”的门槛，但它并没有自动解决另一个问题：

**什么东西值得做？**

Product Reality Check 面向独立开发者、产品经理、创业团队和个人创作者，帮助你在正式投入开发之前，先验证需求、场景、替代方案、价值与获客路径。

它不会一上来就告诉你：

> “这个想法不错，可以先做个 MVP。”

而是从解决方案往回拆：

**想法 → 用户 → 场景 → 现有行为 → 替代方案 → 痛点 → 价值 → 获客 → 产品形态 → 验证**

目标不是把所有想法否掉，而是在修改方向仍然很便宜的时候，尽早暴露那些没有证据支持的假设。

## 它能帮助你回答什么？

例如：

- 这是一个真实需求，还是一个看起来有趣的功能？
- 到底是谁最需要解决这个问题？
- 用户现在是怎么处理的？
- 问题是高频、高损失、高风险，还是只是“有点烦”？
- 有没有真实的付费信号？
- 第一批 100 个用户可能从哪里来？
- 当前设想的产品形态是不是正确？
- 应该先从哪个更窄的细分人群切入？
- 在开发之前，最便宜的验证方式是什么？

## 核心原则

### 行为比观点更重要

“如果有的话我会用”属于弱证据。

已经有人为了这个问题持续花时间、花钱、做手工操作、忍受麻烦，才是更值得关注的证据。

### 替代方案比直接竞品更重要

真正的竞争对手可能不是另一款创业产品，而是：

- Excel / 表格
- 群聊
- 搜索
- 人工流程
- 通用软件
- 临时 workaround
- 什么都不做

所以，“市场上没有同类产品”并不能自动证明这是蓝海。

### 获客是产品发现的一部分

如果不知道第一批用户在哪里，一个好的产品设想依然没有完成验证。

因此这个 Skill 会尽早追问：

> 第一批 100 个用户具体可能从哪里获得？

### 验证成本应该低于开发成本

MVP 不一定是最便宜的验证方式。

更合适的实验可能是：

- 用户访谈
- Landing Page
- Fake Door Test
- Waitlist
- 社区发帖
- 人工服务
- 原型
- 预售
- 搜索需求研究

## 如何使用

你只需要从一句模糊想法开始：

> 我想做一个帮助远程团队减少低效会议的工具。

Skill 不会马上给结论，而会每次提出少量关键问题，例如：

> 什么真实行为让你认为“会议太多”已经痛苦到值得解决？

> 这些团队现在会用什么方式避免、压缩或者替代会议？

> 谁承担的成本最大：管理者、普通成员，还是运营团队？

在证据逐渐清晰之后，它会生成一份 **《产品机会诊断》**。

## 最终输出

通常包括：

1. 重新定义后的用户问题
2. 已有证据 / 未验证假设 / 重大未知项
3. 最主要的失败风险
4. 当前需求状态
5. 2–4 个可能的产品方向
6. 最关键的 1–3 个假设
7. 最小验证实验
8. 继续 / 调整 / 停止的判断条件

它不会用“82 分”“A级项目”这类伪精确评分，而会使用更符合产品发现过程的状态描述，例如：

- 真实需求已有较强证据
- 存在需求，但强度尚未验证
- 需求真实，但商业模式不清晰
- 需求真实，但当前产品形态可能不对
- 解决方案先行，尚未证明存在需求
- 目前更接近弱需求

## 使用方式

运行时使用的精简版 Skill 位于 [`SKILL.md`](./SKILL.md)。

完整的方法论、判断依据和更细的产品发现框架保留在 [`references/methodology.md`](./references/methodology.md)。这样 Agent 实际加载时可以更轻，同时又不会丢失完整框架。

你可以把 `SKILL.md` 复制到支持 Skill / Instruction 的 AI Agent 中，也可以作为项目级提示词或系统指令使用。

示例位于 [`examples/`](./examples/)。

## 适合谁？

- 独立开发者
- Solo Founder
- 产品经理
- 创业团队
- AI Builder
- 经常有产品点子，但不可能全部做出来的人

## 它不是什么？

它不是：

- 点子打分器
- 自动生成市场规模的工具
- 用户访谈的替代品
- 把所有想法包装成创业机会的顾问
- 默认认为原始解决方案正确的 AI
